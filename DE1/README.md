# Документация по выполнению домашнего задания

**Тема:** Создание пяти связанных источников данных, генерация синтетических данных и загрузка в PostgreSQL

## 1. Общая информация

В рамках домашнего задания была реализована упрощенная банковская модель данных. Цель работы состояла в создании пяти логически связанных источников данных, генерации большого объема синтетических записей и последующей загрузке этих данных в базу PostgreSQL.

Выбранная предметная область — банковская система — позволяет естественно связать между собой несколько источников. Один и тот же клиент может присутствовать в нескольких подсистемах: в клиентской базе, в системе счетов, карточной системе, мобильном приложении и транзакционной базе. Такой подход соответствует типовой банковской архитектуре.

## 4. Описание источников данных

В работе были созданы следующие пять источников данных:

### 4.1 Clients

Таблица `clients` хранит основную информацию о клиентах:

* `client_id`
* `first_name`
* `last_name`
* `birth_date`
* `phone`
* `email`
* `city`
* `registration_date`

### 4.2 Accounts

Таблица `accounts` содержит сведения о банковских счетах клиентов:

* `account_id`
* `client_id`
* `account_number`
* `account_type`
* `currency`
* `balance`
* `status`
* `opened_at`

### 4.3 Cards

Таблица `cards` содержит информацию о выпущенных банковских картах:

* `card_id`
* `client_id`
* `account_id`
* `card_number_masked`
* `card_type`
* `card_level`
* `issue_date`
* `expiry_date`
* `card_status`

### 4.4 Mobile_sessions

Таблица `mobile_sessions` моделирует использование мобильного банковского приложения:

* `session_id`
* `client_id`
* `login_time`
* `logout_time`
* `device_type`
* `app_version`
* `ip_address`

### 4.5 Transactions

Таблица `transactions` хранит информацию о финансовых операциях:

* `transaction_id`
* `client_id`
* `account_id`
* `card_id`
* `transaction_time`
* `amount`
* `currency`
* `transaction_type`
* `merchant_name`
* `merchant_category`

Все таблицы связаны между собой через ключевые поля `client_id`, `account_id` и `card_id`. Скрипт генерации дополнительно проверяет корректность этих связей перед сохранением данных. 

---

## 5. Логика связей между источниками

Связи между источниками реализованы следующим образом:

* клиент сначала регистрируется в системе и появляется в таблице `clients`;
* затем клиенту может быть открыт один или несколько счетов, которые сохраняются в `accounts`;
* к счету может быть выпущена карта, которая попадает в таблицу `cards`;
* клиент пользуется мобильным приложением, и его действия фиксируются в `mobile_sessions`;
* при использовании счета и карты создаются записи в таблице `transactions`.

Эта логика соответствует реальному банковскому сценарию: клиент взаимодействует сразу с несколькими системами, но все записи остаются связанными между собой.

## 6. Генерация синтетических данных

Для генерации данных был использован Python-скрипт. Он формирует реалистичные значения с помощью библиотеки Faker и сохраняет данные в CSV- и Excel-форматах.

Скрипт создает следующий объем данных:

* `clients` — 2000 записей
* `accounts` — 3000 записей
* `cards` — 2500 записей
* `mobile_sessions` — 12000 записей
* `transactions` — 30000 записей

Общее количество записей составляет **49 500**, что превышает требуемый минимум в 10 000 записей. Результаты сохраняются в папку `bank_sources_output` и дополнительно в файл `bank_sources.xlsx`.

## 9. Загрузка данных в PostgreSQL

Загрузка данных выполнялась из CSV-файлов с помощью команды `\copy`. Поскольку таблицы связаны внешними ключами, импорт выполнялся в следующем порядке:

1. `clients`
2. `accounts`
3. `cards`
4. `mobile_sessions`
5. `transactions`

Пример загрузки:

```sql id="1lp27q"
\copy clients FROM '/путь/к/clients.csv' CSV HEADER ENCODING 'UTF8'
```

Такой порядок загрузки нужен для того, чтобы сначала загружались родительские записи, а затем зависимые.

## 10. Проверка корректности загрузки

После импорта были выполнены проверочные SQL-запросы:

* проверка отсутствия дубликатов и ошибок по ключам.

```sql id="dfrc7o"

SELECT COUNT(*) FROM transactions;
```
